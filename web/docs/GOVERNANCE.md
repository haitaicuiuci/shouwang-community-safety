# 策略治理方案与职责协作

本文件中“已实现”指代码中可执行能力；所有生产灰度、抽检比例和时限均为建议方案，不代表发生过。

## 策略生命周期

已实现：配置与模型版本分离；冻结阈值保存在 policy.json；源数据、源码、配置、模型与逐样本预测具有哈希；验证搜索只使用验证集；重跑输出到实验库，人工事件保存在独立 operations.sqlite。

当前冷启动策略：字符模型分数≤0.28且规则未命中则通过，≥0.72则拦截，其余进入 LLM 候选；禁用适配器返回 review 后进入人工队列。此为离线路由仿真，未对真实用户执行删除或处罚。验证目标没有迁移到测试，门禁状态为 BLOCKED。

后续版本建议：提出问题 → 产品定义规则与体验 → 运营整理案例及标注 → 算法开发候选 → 冻结参数 → 独立评测 → 安全/隐私检查 → 决策记录。每次发布应绑定数据版本、标签规范、模型、阈值、适配器、操作者、理由与回滚版本。不得用“线上效果好”替代独立证据。

## 人工审核规范

已实现工作台提供独立审核人、理由、通过/拦截/待复核选项，队列不展示源标签，保存操作事件；可发起申诉并重入队。低上下文或有争议时保持待复核。源测试标签用于离线评估，不能自动成为审核人的结论。

建议审核顺序：定位对象与行为 → 识别贬损/威胁/泛化 → 检查引用、否定、反偏见、新闻或讨论语境 → 判断是否缺少上下文 → 选择结论并写依据。身份词本身不能当作处罚证据。待复核队列按模型风险分数降序只为演示；正式流程应增加等待时长、公平性与紧急风险排序。

建议高风险或歧义样本双人独立标注，分歧交第三人仲裁；记录一致率与分歧原因。当前未开展多人标注，没有 Kappa、真实人审准确率或吞吐量。

## 抽检、反馈和申诉

建议分别抽取自动通过、拦截、待复核与申诉样本，分母和采样概率独立记录。例如初始每周各层至少100条或全量不足时全部；这是规划，不是统计充分性的保证。按上线风险和目标置信区间调整样本量。抽检不能只看被用户举报的内容，以免选择偏差。

已实现申诉以事件形式重新入队，历史审核保留，之后可再审；不直接覆盖实验真值。建议申诉由非原审核人复核，并向用户提供具体规则依据和纠错路径。样本回流到隔离候选池，经去重、权限检查、双审和版本审批后才进入新训练集；本 MVP 不自动重训，防止反馈污染和泄漏。

## 灰度与回滚（方案）

只有新留出集达到预注册门槛后，先影子运行，再拟议按1%→5%→20%流量推进，逐段检查误杀、漏放、人审积压与申诉改判。比例仅为示例，没有实际线上流量。生产 Precision 门槛应结合置信下界、风险严重度与样本覆盖，不能沿用本项目95%经验值当保证。

阻断条件建议：任一关键切片超过误杀预算、证据不足、适配器异常增多、人工积压超预算。回滚应保留最近验证的模型/阈值包，切换版本或将自动处罚转人工；不要自动删除历史决策。当前 MVP 提供版本化产物和建议流程，没有生产开关、发布平台或高可用回滚实现。

## 漂移与监测（方案）

监控分数直方图、路由占比、样本长度、未知字符/词特征比例、按话题切片、随机抽检误杀/漏放、申诉改判、人审等待分位数。可用 PSI 等分布指标作告警线索，不能单独证明质量变化。记录参考窗口和当前窗口；异常触发代表性标注与复测，不直接调阈值。

本项目已有静态 SQL 类别、路由、错误与质量查询；未实现线上数据采集、定时监控和漂移告警，因此不会声称持续监控已上线。

## 产品 / 算法 / 运营交付物

|角色|输入与产出|验收关注|
|---|---|---|
|策略运营|案例复盘、审核规范、SQL指标、阈值建议|分母清晰、难例覆盖、反馈可追溯|
|算法|数据切分、模型版本、校准/评测结果|无测试调参、切片误差、性能证据|
|产品/工程|审核工作台、申诉机制、事件日志、故障降级|权限、状态一致性、可用性和用户纠错|
|安全/隐私|数据与供应商使用边界|最小化数据、授权、保留与删除策略|

本地 MVP 的 SQLite 与 loopback 服务没有多用户鉴权、并发审核锁、角色权限或生产数据保留制度，不能直接部署为公网审核系统。
